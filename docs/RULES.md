# 規則

`BRIEF.md` が契約。これはそこに書かれていない、**このプロジェクトが実際に失敗して学んだこと**。

作業を投げるときは `BRIEF.md` とこの文書を読ませる。
経緯と数値は `docs/STATUS.md` にある。**必要になったときだけ引く。**

**ここに時点の事実（Action の件数、テストの件数、機能の一覧）を書かない。**
それらはコードとテストが持っている。文書に書くと必ず古くなり、毎回読む文書に嘘が混ざる。

---

## 測ることについて

**書けたことは、効いたことの証明ではない。**
`SHGetSetSettings` は `void` を返す。`ABM_SETSTATE` は常に `TRUE` を返す。
戻り値も、設定値の読み直しも、効果の証拠にならない。

**「読めた」は「変わった」ではない。**
時計の要素が読めることと、時計の表示が変わったことは別。
判定は必ず**適用前と適用後の差**で行う。片方だけ読んで判定しない。

**「見えない」は「透過している」ではない。**
手前に画面いっぱいの窓があると、透過していてもいなくても同じ結果が返る。
Z 順に依存しない測り方（窓自身の性質）を別に持つ。

**0 件が出たら、計器を先に疑う。**
「無かった」なのか「数えられなかった」なのかを、出力から区別できるようにする。
区別できない 0 は成果ではない。

**測れなかったことを合格にしない。**
前提が満たされないなら `measured=false reason=...` を出す。黙って `return` しない。
見送りを合格として読ませない。どこに証拠があるかを見送りの文言に書く。

**同じ値を書いて同じ値が返っても、何も証明していない。**
往復テストは、必ず**今と違う値**を書く。元と同じ値だったら「測れなかった」と出す。

**自分の書き込みを自分で読み返して確かめない。**
可能なら別プロセスから観測する。座標も、ピクセルも、プロセス ID も。

**計器を、既知の不良で先に確かめる。**
禁止語のテストなら禁止語を入れて落ちることを見る。透過なら透過しない窓で見えることを見る。
落ちない計器の合格には意味がない。**自分で書いた検出スクリプトも計器。**

**名前から結果の向きを推測して、それを合格条件にしない。**
「高コントラスト」は、白地に黒よりコントラスト比が下がる。測ったら逆だった。

## 戻すことについて

**戻す先は「既定値」ではなく「変更前の値」。**
利用者が独自の設定にしていることがある。既定値を書くのは復元ではない。

**元の値が読めないなら、戻せると言わない。**
`LampArray` は色の setter が 6 つあって getter が無い。戻せないものは作らない。

**第三者の変更を上書きしない。**
現在値が自分の適用値でも元の値でもないなら、`ExternalConflict` で止める。取り返さない。

**複数の値を書くなら、1 バイトも書く前に全部を見る。**
書きながら判定すると、途中で止まって半分だけ戻った状態が残る。

**補償の結果を捨てない。**
`let _ =` で握り潰すと、「失敗した」が「何も変わっていない」と読まれる。
巻き戻せたことを読み直して確かめる。確かめられないなら `RecoveryRequired`。

**強制終了で残るものを作らない。**
`Drop` は kill では走らない。書く前に「戻す先」をディスクへ残し、次の起動で戻す。

**利用者が手で変えたら手を引く。**
取り返さない。取り返すと、人と機械が同じ設定を取り合うことになる。

**その機能の出番が無い環境では、何も書かない。**
元から常に隠している人、既に高コントラストの人、Windows が既定プリンターを管理している人。
「出番なし」と出して終わる。

## 言うことについて

**測っていない効果を約束しない。**
速くなる／FPS が上がる／遅延が減る／安全／絶対／保証。
効果を否定する文（「速くなるとは言えません」）は書いてよい。約束だけを禁じる。

**原因を断定しない。**
値が違っていても、原因が Windows Update だとは限らない。
時間的に近いことは因果ではない。「違います」までにする。

**分からないものを「大丈夫」に混ぜない。**
確認できなかったものは別の欄に出す。件数にも現れるようにする。

**空の一覧で「ありません」と断定してよいのは、読めたうえで 0 件だったときだけ。**
安全コアへ繋がっていないときに「まだモードはありません」と書くと、
登録済みのものが消えたように見える。`dataMode` を見てから書く。
（これを機械的に見張るテストを一度書いたが、フィルタ結果や説明文まで拾って
誤検知が本物を上回った。**騙る計器はテストとして置かないほうがよい。**）

**作用範囲どおりに書く。**
「すべてのマイク」ではなく「既定の通話マイク」。届かない相手がいるならそう書く。

**API 名・レジストリパス・GUID・内部 ID を画面に出さない。**
利用者の言葉で書く。ウィンドウタイトルとファイル名は個人情報として扱う。

## テストについて

**テスト名が主張していることを、そのテストが本当に assert しているか。**
「bit と作業領域の両方を見る」と名乗って bit しか見ていない、
「cpu」と名乗って測っていない、という例が実際にあった。

**関数本体を定数に置き換えても緑のままなら、そのテストは何も証明していない。**

**`#[ignore]` でない通常のテストの早期 return は、より悪い。**
毎回走って「N 件通った」に数えられる。飛ばしたことを出力に残す。

**分解能の底に張り付いた数字を、測定値として読まない。**
`GetProcessTimes` は 15.625ms 単位でしか刻まない。
5 秒で 15625us と出たらそれは 1 ティックであって、上限しか言えない。

**実機の共有設定を触るテストは直列化する。**
マウス設定もタスクバー状態も 1 つしかない。並列に走ると互いを第三者の変更として観測する。

## 版が上がったときについて

**耐久記録に残る文字列を、後から変えない。**
`ActionId` は `rename_all = "snake_case"` が効いている。`rename` を1つ書き忘れた版は
`power_mode_switch` の形で記録を書く。`rename` を足した後の版はそれを読めず、
**その変更は永久に戻せなくなる。** 書き忘れは実際に2回起きた。
だから各 variant は点表記と snake 表記の**両方を `alias` で受ける**。書き出すのは点表記のまま。

**`rename_all` の分解は variant 名に対して起きる。**
`SetupPowerToysStatus` は `setup_power_toys_status`。点表記を `_` に置き換えた形とは限らない。

## 同時に起きたときについて

**Windows の設定を書く経路は、必ずプロセス間のロックを取る。**
監視スレッドだけ例外にしない。相手の「読む → 比べる → 書く」に割り込むと、
割り込まれた側は自分の書き込みが第三者に変えられたと観測する。

**ロックが取れなければ、その回は書かない。** 待たない。監視は繰り返すので取り戻せる。

## 手で揃える表について

新しい Action を足すとき、次が揃っていないと**画面から呼べない**か、**一覧ごと落ちる**。
コンパイルは通る。単体テストも通る。

- `ActionId` と `ActionParameters` の**両方**に `#[serde(rename = "...")]`
  （`ActionId` の分は耐久バックアップの表記になる。既存データがあるなら `alias` を残す）
- `action/registry.rs` の登録配列
- `permissions/application-commands.toml`
- `lib.rs` の `invoke_handler`
- `src/App.tsx` の `parametersForAction`
- `src/catalog.ts`
- 件数テスト、README の内訳表、CHANGELOG

`request_round_trip`、`category_contract`、`count_report` が見張っている。**必ず通す。**

## 数え方について

**区分の合計が総数と一致することを assert する。**
`_ => {}` で 1 区分を黙って捨てていて、README の内訳表がそのズレを写していた。

## 他のモデルの出力について

**引用された行が実際に存在するかを最初に確かめる。** これが最も歩留まりの良いフィルタ。
存在しない行を根拠にした指摘が、いちばん多かった不良の形。

**指摘の数と当たりは比例しない。** 24 件出して 1 件、0 件と答えて前回 2 件、という実測がある。

**同じモデルに自分の書いたコードを監査させると、思い込みごと通過する。**
別系統を当てると、そこが割れる。
