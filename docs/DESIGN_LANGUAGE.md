# PCカスタム デザイン言語（CC主導・実装の拘束条件）

目的: 「AIが作ったっぽい」汎用SaaS顔を排除し、**Windowsにネイティブに馴染みつつ、巷で評価の高いプロダクトの良さを取り込んだ、静かで信頼できる**見た目にする。実装はこの指針に従う。逸脱する場合はCC承認を得る。

## 参照プロダクトと「何を borrow するか」
- **Linear** — 静かな高密度・抑制された中間色＋1アクセント・目的のあるマイクロモーション・優れた空状態。→ 全体トーン、型階層、⌘K/Ctrl+K コマンドパレット。
- **Raycast** — アクション/コマンドの心的モデル（PCカスタムは Action ベースなので直結）。→ 「結果を選ぶ」リスト＋右詳細ペイン、キーボード主導。
- **Apple Shortcuts** — 結果ファーストのカード、「〜のとき〜する」自動化ビルダー。→ カード比喩、平易語の Mode/トリガー UI。
- **Steam ライブラリ / Playnite** — ゲームライブラリ、ゲーム別プロファイル、カバーアート、プレイ前チェック。→ ゲームプロファイル画面、準備チェックの preflight パネル。
- **1Password / Proton** — セキュリティ製品の信頼前面設計。誇張せず正直に「何が起きるか」を見せる。→ Action の属性パネル（現在→適用後・危険度・戻せる）、変更タイムラインの透明性。
- **Windows 11 Fluent / WinUI / 設定アプリ** — ネイティブ感。→ **Mica**背景、角丸、**Segoe UI Variable**、**システムアクセントカラー追従**、Fluent モーション、正しい light/dark。

## 絶対に避ける（anti-AIデザイン）
- 汎用の紫/藍グラデ・ヒーロー、全要素センター寄せ、絵文字をアイコン代わり、均一な角丸カードの敷き詰め、Inter一択の無個性、意味のない影の乱用、ロレム。
- アクセント色に**ランダムなSaaS紫を使わない**。既定は**OSのシステムアクセント**を読み取り追従（＝ネイティブで無個性でない）。フォールバックは落ち着いた青緑系。
- 意味を色だけに依存させない（危険度は色＋ラベル＋アイコン）。

## デザイントークン
- **色**: ニュートラル基調。light=面 #FAFAFA/#FFF・文字 #1A1A1A、dark=Mica上の半透明面・文字 #F3F3F3。アクセント=システムアクセント（取得不可時フォールバック #2FA6A0）。危険度: 安全=緑系、注意=amber、実験的=violet/赤アウトライン。本文コントラスト **WCAG AA 4.5:1** 以上。
- **タイプ**: Segoe UI Variable（無ければ Inter）。スケール 12/13/14/16/20/28、太さで階層を作る（本文400・見出し600）。
- **余白**: 4px グリッド、詰め込まず余白で階層。**半径**: カード8px・コントロール6px。**影**: 極薄1段のみ。
- **モーション**: 150–250ms ease-out、状態変化（適用/復元）に意味のある動きだけ。`prefers-reduced-motion` 尊重。

## 主要画面
1. **ホーム** = 設定一覧にしない。**結果タイル**を並べる: ゲームを快適に / 見た目を変える / 邪魔な表示を減らす / 新PCをセットアップ / 集中する / 容量を空ける / 変更を元へ戻す。
2. **カテゴリ → Actionカード**（Raycast風: 左リスト＋右詳細）。カード内: 結果タイトル・1行説明・**現在→適用後**の状態行・属性チップ（危険度/管理者/再起動/Update影響/戻せる）・ボタン（詳細を見る/適用/プロファイルへ追加）。
3. **適用プレビュー確認**: 実際に変わる内容を差分的に明示してから適用（透明性）。
4. **タイムライン**: 各項目に「この変更だけ戻す/この時点まで戻す/内容/結果/失敗だけ再試行/ログ」。
5. **Mode/プロファイルビルダー**（Shortcuts風）: トリガー → Actionセット。初期は手動＋アプリ起動/終了。
6. **ゲームプロファイル**: カバー、**準備チェック preflight**（Hz/HDR/GameMode/電源/空き容量/音声出力/マイク/通知）、起動時/終了時の Action セット。
- **コマンドパレット**（Ctrl+K）: 任意の結果へジャンプ。

## アクセシビリティ / ネイティブ
キーボード主導・可視フォーカスリング・スクリーンリーダーラベル・AA コントラスト・色のみ依存禁止。ウィンドウは Mica、タイトルバーはネイティブ or 統合カスタムでも Windows 標準の閉じ/最小/最大挙動を守る。

## 品質バー
初回起動の空状態、ローディング/失敗/権限不足の各状態、長い一覧の仮想化、ダーク/ライト両対応スクリーンショットを必ず用意。「動く」だけでなく**静かで洗練され、Windowsに馴染む**ことを合格条件にする。

### 監査で見つけて直した実欠陥

1. `--text-tertiary: #747474` はライト地で **4.48:1** と AA にわずかに届かなかった → `#6b6b6b`（約5.0:1）へ。

- 実行中に配色スキームを切り替えると、一部要素の背景が旧テーマのまま計測されることがある（WebViewの再描画都合）。再読込後は正しい値になるため、アプリの欠陥ではない。
- `color(srgb …)` 形式の背景を旧監査スクリプトが誤読して不合格に見えていた。パーサ修正後は解消。

## 実画面を見て直した点（CC 2026-07-26）

ヘッドレスブラウザで実画面を撮り、参照プロダクト（Linear の静かな秩序、Raycast の一定したリズム）と
見比べて直した。

1. **結果タイルのグリッドが不揃いだった** — `repeat(6, 1fr)` に対し先頭2枚が3列、残りが2列で、
   6枚目が1枚だけ取り残されていた（2→3→1の階段状）。`repeat(3, minmax(0,1fr))` の均等3列×2行へ変更。
   実測でタイル幅が6枚とも 322px で揃ったことを確認。
2. **日本語の行末に「す。」だけが落ちていた** — 「まとめま／す。」のような孤立。
   `text-wrap: pretty` と `line-break: strict` を本文系に適用し、「まとめ／ます。」へ改善。
3. **ホームの一文が実態と合っていなかった** — 「61件の登録済みActionから安全な候補を表示します」は、
   実際には大半が表示専用である事実を隠していた。
   「登録済みの61項目から、いまのWindowsで実際に変えられるものを見分けて表示します」へ変更。
   これは実測で6件の不作動Actionを見つけた今、**このプロダクト固有の価値**でもある。

再監査: コントラスト不合格 0（ライト/ダーク）、横あふれなし、タイル幅均一。

### 参照プロダクトから取り入れたパターン（実装）

見比べて直すだけでなく、参照先の**中核パターン**を実装した。

**Raycast / Linear — 一覧はキーボードだけで辿れる**

両者に共通する最も本質的な操作感は、手をキーボードから離さずに一覧を移動でき、
選択に応じて詳細が追従することである。PCカスタムにはコマンドパレット（Ctrl+K）にしか
矢印移動が無く、**主役であるAction一覧は矢印キーで動かなかった**。

実装: `.action-list` に `ArrowDown` / `ArrowUp` / `Home` / `End` を実装。
選択が動くと右の詳細ペインが追従し、フォーカスも該当行へ移り、`scrollIntoView` で視界に入る。

実測（18項目のファイル表示カテゴリ）: ↓×3 で `show_extensions` → `item_checkboxes`、
↑ で1つ戻り、`End` で最終項目へ。フォーカスは常に行に残ることを確認。

**Raycast / Linear — できることは、できると書いてある**

矢印で辿れるようにしただけでは足りない。両者は必ず画面のどこかに操作ヒントを置いている。
PCカスタムのコマンドパレットには既に `↑↓選択 / Enter開く / Esc閉じる` があったが、
今回追加したAction一覧の矢印移動には何も出ておらず、**誰も気づけない機能**になっていた。

一覧見出しの右に `↑ ↓ で移動` を追加。実測でコントラスト 6.36、
最初 9px にしてしまい自分で定めた型階層（12/13/14/16/20/28、補助は10px）を割っていたので 10px へ修正。
**機能を足したら、それを知る手段も足す。**

**Apple Shortcuts — 自動化は文章として読める**

Shortcuts の要点は、組んだ自動化が「〜のとき、〜する」という**一文として読める**ことにある。
PCカスタムのプロファイル作成は、名前・実行ファイル・チェックボックス一覧という素のフォームで、
入力し終えるまで何が起きるのか分からなかった。専門用語を見せない方針と噛み合っていない。

フォーム冒頭に、入力へ追従する一文を置いた。

> **VALORANT** が始まったら、**3件の準備**をして、終わったら**変更した分だけ元に戻します**。

未入力時は「このゲーム」「選んだ準備」と出るので、書き始める前から何を作っているのか分かる。
実測: 名前を入力すると「このゲーム」→「VALORANT」へ即座に変わることを確認。

### 手動モード追加に伴うUI整合（CC 2026-07-26）

codexが手動モード（勉強・作業）を実装したので、画面側の辻褄を合わせた。

1. **ナビが「ゲームプロファイル」のままだった** — 中身はゲーム専用ではなくなったのに、
   サイドバーだけゲームと言っていた。「モード」へ変更。
   Actionをモードへ追加できないときの文言も、ゲーム限定に読めたので直した。
2. **ホームの導線がBRIEFの一覧に足りていなかった** — BRIEF §UI方針が挙げるうち
   「勉強・作業に集中する」「新しいPCをセットアップする」「容量を空ける」の3つが無かった。
   タイルからカテゴリ以外の画面（モード／セットアップ）へも飛べるようにして追加。
   9枚になったが3列×3行で均等（実測 317px×9枚）。

実測: タイルから「勉強・作業に集中する」→モード画面、「新しいPCをセットアップする」→セットアップ画面へ
遷移することを確認。コントラスト不合格0、横あふれなし。

なお手動モード自体のUIは、切り替えると
「このモードを『いま実行』したら、選んだ準備をします。アプリ起動は元に戻しても終了しません。」
と文章が変わり、実行ファイル欄も消えることを実画面で確認した（Shortcuts の作法が手動側にも効いている）。


## アクセント色は文字に使えない（2026-07-26 実測）

`--accent` は `@supports (color: AccentColor)` で **`AccentColor`** に差し替わる。
これは **Windows のユーザーが選んだ色**で、我々の管理外だ。何色になるか事前に分からない以上、
**文字色として使うとコントラストを保証できない。** 面の装飾（背景・縁取り）と
`accent-color`（フォーム部品の着色）に限る。

実測で落ちていたのは `.link-button` の 2.87:1（14px）。ほかに8箇所が文字色に使っていた。

- 成功だけを表す表示（`.setup-card__result--ok` / `.profile-state--on` /
  `.powertoys-status__mark--installed`）→ `--safe` / `--safe-soft`。意味も合う。
- 成否どちらも同じ要素に出るメッセージ（各パネルの `__message`）→ `--text-secondary`。
  成功色で塗ると**失敗が緑で表示される**。
- リンク（`.link-button`）→ `--text` ＋ 下線。色ではなく下線と太さで区別する。

## 半透明の面では白地の計算が通用しない（2026-07-26 実測）

`--surface` は `rgba(255,255,255,0.76)` の Mica 風。実効背景は白より暗いので、
**白地で 4.5:1 を満たす色が実測で落ちる**。`--text-tertiary: #6b6b6b` は
白地なら 5.33:1 だが、合成後の実効背景では **4.23:1** だった。`#656565` へ。

コントラスト計測は祖先の背景を根から順にアルファ合成して求めること。
「不透明な祖先が見つかるまで遡る」式の計測は、半透明の面を素通りして嘘の値を出す。

## 日本語の下限は 10px（2026-07-26）

9px 指定が5箇所（`.compatibility-grid dt` ほか）残っていた。いずれも 10px へ。
初回の監査で見逃したのは、詳細パネルが閉じていて**描画されていなかった**ため。
コントラスト監査は「描画されている要素しか見ない」ことを忘れない。

## 計器の自己検査を先にやる（手順）

コントラスト監査が 0 件を返したとき、**直った**のか**測れていない**のかは区別がつかない。
わざと低コントラストの要素を注入し、それを検出できることを確認してから本番の数字を信じる。
今回この手順で、白地を前提にした最初の計測が 78 件という嘘の数字を出していたことに気づけた。

## 「見にくい・わかりにくい・使いにくい」の実測診断（2026-07-27）

文字を大きくしたが「大きさとは関係なく見にくい」と言われた。測ったら原因が別にあった。

| 画面 | 可視要素 | 文字数 | 箱 | 文字サイズ種類 |
| --- | --- | --- | --- | --- |
| PCセットアップ | 311 | 2,633 | 91 | **16** |
| Action | 211 | 616 | 34 | 7 |
| モード | 140 | 826 | 29 | 12 |

### 病巣1: 文字サイズが16種類、しかも差が0.1〜0.5px

```
11.5 / 11.6667 / 11.84 / 12 / 12.48 / 13 / 13.44 / 13.76 / 14 / 14.08 / 14.4 px
```

11.5〜14.4px の間に11種類。**階層としては見えないのに、不揃いとしては見える。**
いちばん悪い状態だった。

**これは直前の「文字を大きくする」作業で自分が悪化させた。** `.84/.86/.88/.9/.92rem` を
作り、1px 以内に5段を詰め込んだ。階層を増やしたつもりでノイズを増やしていた。

対処: `--fs-xs/sm/base/md/lg/xl/display` の7段に固定し、CSS から生の `font-size` を全廃。
既存値は最も近い段へ1パスで写像した（連鎖置換は多段適用されるので使わない）。
結果 **16種類 → 6〜7種類**（12/13/14/16/19/24/28）。

### 病巣2: 箱が91個

`everyday-feature-card` × 12 と `provider-badge` × 12 で、1パネルだけで24箱。
バッジの中身は「PowerToys」「Windows標準」の**2種類しかなかった**。
二択を伝えるために同じ文字を12回並べていた。

対処: 提供元でグループ分けし、見出しで1回ずつ言う。カード12枚は枠1つの行リストへ。
**目が拾う対象が12箇所から2箇所になった。**

### 病巣3: 1画面が3つの仕事をしていた

PCセットアップ画面に「Windowsの仕上げ」「普段使いの機能」「アプリ導入」が同時に載っていた。
だから2,633文字になる。**画面に目的が1つないのが「わかりにくい」の本体。**

対処: 目的別のタブ（`.segmented`）で一度に1つだけ見せる。

### 結果

| | 前 | 後（最も重いタブ） |
| --- | --- | --- |
| 可視要素 | 311 | 197 |
| 文字数 | 2,633 | 1,308 |
| 箱 | 91 | 60 |
| 文字サイズ種類 | 16 | 6 |

「アプリを入れる」タブは 91要素 / 492文字 / 箱20。全画面・全タブでコントラスト不合格0件、
最小12px、文字切れ0、横あふれなし。

### 教訓

**「見にくい」を文字サイズの問題だと決めつけない。** 数えると、要素数・箱の数・
サイズの種類数・1画面あたりの文字数のほうが効いていた。感想ではなく数を見ること。

## Action 詳細を読んだら、内部識別子が利用者に見えていた（2026-07-27）

密度を数えるだけでは足りず、**画面に出ている順にそのまま読んだ**ら別の問題が出た。

```
低リスク
session.prevent_sleep                          ← 内部 Action ID がそのまま見えている
このモード中は自動スリープを防ぐ                ← 本来これが最初
（説明）
v1                                             ← 利用者に意味がない
...
Windows公開API SetThreadExecutionStateの専用lease  ← 主導線に専門用語
危険度: 低リスク                                ← 冒頭の「低リスク」と重複
...
[詳細を見る] [適用プレビュー] [自動適用の対象外]
```

BRIEF は「設定名ではなく得たい結果から選ぶ」を要求している。**設定名より悪く、内部識別子が出ていた。**
そして一番大事な「何ができるか」が3番目だった。

`自動適用の対象外` は **`disabled` かつ条件的に永久に有効にならないボタン**だった。
押せないものは操作ではなく状態なので、ボタンではなく文で書く。

### 直した結果

| | 前 | 後 |
| --- | --- | --- |
| 最初に出る情報 | 危険度 → 内部ID → 名前 | 名前 |
| 詳細の行数 | 21 | 17 |
| ボタン | 3（うち永久無効1） | 2（永久無効なし） |
| 残る専門用語 | 4種類 | **0** |

内部IDと版と方式は「詳細を見る」の中へ移した。消してはいない。必要な人には見える。

### 教訓

**数を数えるだけでは足りない。画面に出ている順に声に出して読むと、数字に出ない問題が出る。**
密度の指標（要素数・箱・サイズ種類）は「見にくい」を捉えるが、
「わかりにくい」は読み順と語彙にある。

## 画面を初めて見た（2026-07-28）

このセッションを通じて、**私はこのアプリを一度も見ずにUIを直していた。**
ブラウザペインが表示されておらずスクリーンショットが撮れないため、
検証はすべて DOM から数字を取る形で行っていた。
利用者は見ていて、こちらは測っていた。噛み合わないのは当然だった。

ヘッドレス Chrome で撮れることを思い出して撮影したところ、数字では出なかったものが一目で出た。

### 撮影手順（画面遷移込み）

アプリは URL ではなく内部状態で画面が変わるため、単純な `--screenshot` では初期画面しか撮れない。
`dist/__shot.html` に同一オリジンの iframe を置き、ハッシュで指定したラベルのボタンを
順にクリックしてから撮る足場を用意した。

```bash
chrome --headless=new --window-size=1220,900 --virtual-time-budget=6000 \
  --screenshot=out.png "http://localhost:4173/__shot.html#PCセットアップ>普段使いの機能"
```

### 見て初めて分かったこと

- **カードと地の明度差が 1.2 しかなく、境界が沈んでいた。**
  文字と背景のコントラスト検査は AA を満たしていたので、この監査では絶対に出ない。
  **文字が読めることと、面が面として見えることは別の検査である。**
- ホームの10枚が完全に同じ見た目。アイコンの大きさも色も同一で、
  どれから始めるべきかを示すものが何もない。これが「項目多くて何が何だか」の正体。
- Action 画面は左パネルの8割をカテゴリ一覧が占め、実際に選ぶ Action 一覧が最下部にある。
  **「下まで行って項目を押し、上まで戻って適用」という導線はこの配置が作っていた。**
- セットアップ画面に `MMDeviceEnumeratorで実デバイスを読み取り` `UserChoiceを直接書き換えず`、
  モード画面に `.exe のフルパス` `本人性（ファイル識別子）` が残っていた。
  以前の用語チェックは Action 詳細しか見ておらず、他画面を見ていなかった。

### 直した分

面の明度差を 1.21 → 1.44 へ広げ、枠と影で面を起こした。改善はしたが**まだ弱い**。
10枚が同列に並ぶ限り、コントラストをいくら上げても「どれから」は解決しない。
次にやるべきは推奨の提示であって、面の磨き込みではない。

### ブラウザペインのダーク判定は信用できない

`resize_window(colorScheme: dark)` を指定すると `matchMedia` はダークと答えるが、
CSS のメディアクエリはライトのまま評価されていた（`--surface` 変数はダーク値なのに
カードの `backgroundColor` はライト値、という矛盾で発覚）。
**このペインで測ったダークモードの数値は信用しないこと。** 実描画はヘッドレス撮影で確かめる。
