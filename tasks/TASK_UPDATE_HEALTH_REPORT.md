# タスク: Windows 更新後の健全性レポート

`BRIEF.md` が契約。`docs/STATUS.md` の失敗記録を先に読むこと。
自分が書いた `docs/RESEARCH_FEATURES.md` の「3. Windows 更新後のカスタマイズ健全性レポート」を実装する。

## 作るもの

**第1段階のみ。完全に read-only。Windows を1バイトも変更しない。**

いま検出できる各項目の状態を、利用者が明示的に取った基準と突き合わせて、
「基準どおり」「基準と違う」「確認できない」に分けて見せる。

## 絶対に守ること

### 「Windows Update のせい」と書かない

これがこのタスクで一番大事なところ。

更新の直後に値が違っていても、**原因が更新だとは限らない。**
利用者本人が変えたかもしれないし、別のアプリかもしれない。
時間的に近いことは因果ではない。

画面には「基準と違います」とだけ書く。**「Windows Updateで戻されました」とは書かない。**
更新日時を併記するのはよいが、それは**参考情報**であって原因の断定ではない、と分かる書き方にすること。

### 分からないものを「大丈夫」と言わない

検出できない項目は「確認できません」と出す。**「基準どおり」に混ぜない。**
このプロジェクトは `unknown` を `unknown` のまま出すことを価値にしている。

### 基準は利用者が明示的に取ったものだけ

比較の基準にしてよいのは次のどちらか。

1. 利用者が「今の設定を控える」で書き出した config snapshot
2. Action ごとの、直近で成功した適用値（journal にある）

**推測で「本来こうあるべき」を作らないこと。** 基準が無ければ「基準がありません」と出す。

## 使えるもの

- `config_snapshot.rs`: 現在状態の書き出しが既にある
- `journal/repository.rs`: 適用履歴
- 各 Action の `detect_current_state`
- `windows/update_status.rs`: Windows Update の状態読み取りが既にある

## 画面

新しい画面は作らず、**タイムライン画面の中**か、ホームの推奨の隣に置く。
判断は任せるが、**画面をもう1つ増やして「項目が多くて分からない」を悪化させないこと。**
`docs/DESIGN_LANGUAGE.md` に、密度を測った記録がある。読むこと。

文言は日本語。API 名やレジストリパスを画面に出さない。

## 検証

- 基準が無いとき「基準がありません」と出ることをテストで固定する
- 検出できない項目が「確認できません」に入り、「基準どおり」に**混ざらない**ことを固定する
- 値が違うときに「Windows Update が原因」と**書かない**ことを、文言のテストで固定する

実機テストは不要（read-only なので）。ただし**単体テストで上の3点を必ず固定すること。**

## 完了条件

- `cargo test --lib` が全部通る
- `cargo clippy --all-targets -- -D warnings` が通る
- `cargo fmt --check` が通る
- `npm run build` が通る
- **Windows を変更するコードを1行も足していないこと**

ビルドが通らないコードを返さないこと。
